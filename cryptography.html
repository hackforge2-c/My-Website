What exactly does TLS provide?

TLS provides several important security properties.

Confidentiality :
Attackers shouldn't be able to read the contents of the connection.

Integrity :
Attackers shouldn't be able to silently modify messages.

Authentication :
The client can verify that it is communicating with the intended server, based on the server's certificate and the trust chain.

HASHING

Integrity

Hashing in cybersecurity is a process that transforms data of any size into a fixed-length string called a hash value or digest.

It’s primarily used to verify data integrity rather than to encrypt or hide information.

Hashing is generally a one-way transformation.

Input → Hash function → Hash

Example:

"hello"
↓ SHA-256
2cf24dba...

You don't decrypt SHA-256.

SHA-256

SHA = Secure Hash Algorithm
SHA-256 generates a:

256-bit hash

It is commonly used for:

  • integrity checking
  • digital signatures as part of signature schemes
  • certificates and fingerprints
  • software/file verification
  • blockchain-related applications

Important:

SHA-256 is a hash function, not an encryption algorithm.

While SHA-256 is highly secure for checking file integrity or locking down blockchain transactions, it is dangerous to use for passwords because it is too fast.

If a hacker steals a database of SHA-256 hashes, they can use powerful computer graphics cards (GPUs) to guess and check billions of passwords every second, easily cracking common passwords almost instantly. Password-specific hashes (like Bcrypt) are intentionally designed to be slow to block these automated attacks.

Live demo · the avalanche effect (real SHA-256)
🧠 MEMORY TRICK Hash = fingerprint, not a lock. Same finger → same print. One tiny change → a completely different print. And you can't rebuild a finger from a print.
03

SALTS (PREVENT RAINBOW TABLES)

Passwords

The problem: the same input always gives the same hash.

User A: "password123" ──SHA-256──> ef92b778...
User B: "password123" ──SHA-256──> ef92b778... (identical!)

If an attacker steals the database, they can see that A and B share a password. They can also use a rainbow table, a huge precomputed list of password → hash pairs, and look the hash up instantly.

The fix is a salt: a unique random value generated per user and added before hashing.

User A: "password123" + salt "k8Zq1" ──hash──> 91ab03...
User B: "password123" + salt "Xp7mW" ──hash──> c47e5d... (different!)

What’s stored in the database:

User table
├── username
├── salt (random, unique per user)
└── password_hash

Important points:

  • A salt is not secret. It’s stored next to the hash.
  • Its job is to make precomputed tables useless and make identical passwords look different.
  • A pepper is an extra secret value stored outside the database (for example in a KMS). It’s optional.

The demo uses plain SHA-256 only to show the effect of salting. Real systems use bcrypt / Argon2id (below).

Which algorithm to use

SHA-256 ──> too fast, bad for passwords
bcrypt ──> slow on purpose, salt built in, adjustable "cost"
scrypt ──> slow, memory-hungry
Argon2id ──> memory-hard, currently the top recommendation

Remember:

Passwords → Salt + slow hash (bcrypt / Argon2id)
Files → SHA-256
📊 Hash families compared by use case, security level and speed
🧠 MEMORY TRICK Salt = a pinch of random per user. Fast hash for files (you want speed), slow hash for passwords (you want the attacker slow). “Files fast, passwords slow.”
04

KEY MANAGEMENT

Critical

Encryption is only as strong as the protection of the key. AES-256 is useless if the key is lying in your source code.

Things to make note of :

Bad:

SECRET_KEY = "mySuperSecretKey123" # hardcoded, ends up in Git

Better:

import os
SECRET_KEY = os.environ["SECRET_KEY"] # injected at runtime

Best for production: a secrets manager or KMS (AWS KMS, Azure Key Vault, HashiCorp Vault).

Level 1: hardcoded in code ❌
Level 2: environment variables ✅ baseline
Level 3: secrets manager / KMS ✅✅ recommended
Level 1
Hardcoded in code
❌ Unsafe
Level 2
Environment variables
✅ Baseline
Level 3
Secrets manager / KMS
✅✅ Best

Good practices:

  • Never commit keys to Git (scanners like gitleaks and trufflehog look for this).
  • Rotate keys regularly.
  • Keep keys separate from the data they protect.
  • Give access to as few people and services as possible.
🧠 MEMORY TRICK Never leave the key under the doormat. A strong lock (AES-256) with the key taped to the door (hardcoded) is no lock at all. Four habits: No Git · Rotate · Separate · Least access.

Common Algorithms: Symmetric vs Asymmetric

Reference

You already know AES (symmetric, same key both ways). The other type is asymmetric.

RSA uses a key pair:

Public key → can be shared with everyone
Private key → kept secret

Encryption(Asymmetric) :

Plaintext ── (public key) ──> Ciphertext ── (private key) ──> Plaintext

Digital signature (the reverse direction):

Message ──(private key signs)──> Signature ──(public key verifies)──> ✔ authentic

Why use both? Asymmetric crypto is slow, and symmetric crypto is fast. TLS combines them:

1. Asymmetric crypto (RSA / ECDHE) → safely agree on a secret key
2. Symmetric crypto (AES) → encrypt the actual data fast

🧠 MEMORY TRICK Public = padlock, Private = its only key. Anyone can snap a padlock shut (encrypt with the public key), only the owner has the key to open it. And: Asymmetric to agree, symmetric to talk.

Digital Signatures

A digital signature is the electronic equivalent of a handwritten signature, but much harder to forge. It proves three things about a message or file.

Digital Signature
│
├── Authenticity → who created/sent it
├── Integrity → it wasn't changed after signing
└── Non-repudiation → the signer can't later deny signing it

Note what it does not provide: confidentiality. A signed message can still be readable by everyone. Signing is about trust, not secrecy.

The key idea: the direction is reversed

Encryption and signing both use a key pair, but the keys are used in opposite roles.

Encryption (confidentiality):
Sender uses RECEIVER'S PUBLIC key → only the receiver's PRIVATE key can open it

Signing (authenticity):
Sender uses THEIR OWN PRIVATE key → anyone with the sender's PUBLIC key can verify it

Only you hold your private key, so only you can produce a valid signature. Everyone has your public key, so everyone can check it.

Avoid
MD5 → collisions can be created practically; broken
SHA-1 → collisions demonstrated; deprecated
DES → 56-bit key, brute-forced easily
3DES → small 64-bit blocks; deprecated
RC4 → biased output; banned in TLS
ECB mode → same plaintext block = same ciphertext block (leaks patterns)

ECB is why the famous “encrypted penguin” image still looks like a penguin. Use AES-GCM instead.

In ECB the colours changed but the shape is still easy to see. That is the leak. Good modes hide the shape completely.

Rule: never invent your own crypto. Use a well-tested library.

07

CERTIFICATES (SSL/TLS)

Trust

The problem :

How do I know the public key I received really belongs to bank.com?

What if a hacker gives you his own public key and says “Hi, I’m bank.com”? You would send your password to the hacker.

You ──"Give me bank.com's key"──> Internet
│
Hacker replies: "Here is bank.com's key" (but it's the hacker's!)

We need someone trustworthy to confirm: “Yes, this key really belongs to bank.com.”

The solution: a certificate

A certificate is like a government ID card for a website.

Think about your Aadhaar or passport:

PassportWebsite certificate
Your nameDomain name (bank.com)
Your photoWebsite’s public key
Valid till dateValidity dates
Stamp from the governmentSignature from a CA

You trust a passport because the government issued it, not because the person says “I’m Vishu.”

In the same way, you trust a certificate because a Certificate Authority (CA) signed it.

Certificate
├── Domain name (bank.com) → "who am I"
├── Server's public key → "here is my key"
├── Validity dates → "valid from ... to ..."
└── Signature from a CA → "a trusted authority confirms this"

The CA’s signature is the same digital signature you just learned about. The CA uses its private key to stamp the certificate.

Examples of CAs: Let’s Encrypt, DigiCert, Sectigo, GlobalSign.

Your browser can’t know every website, but it knows a small list of very trusted organizations (Root CAs). Their details come pre-installed in your browser and operating system.

Root CAs are too valuable to use every day, so they authorize helpers (Intermediate CAs). The helpers sign the actual website certificates.

Root CA (pre-installed in your browser, super trusted)
│ signs
▼
Intermediate CA (helper, trusted because Root signed it)
│ signs
▼
bank.com certificate

Easy example: a company

  • Root CA = the CEO (everyone trusts the CEO)
  • Intermediate CA = a manager (trusted because the CEO appointed them)
  • Website certificate = an employee ID card (valid because the manager signed it)

The browser follows the chain upward: “bank.com was signed by the manager, the manager was signed by the CEO, and I trust the CEO. OK!”

Everything in one story

You open bank.com on your phone:

  1. Browser asks for the certificate: “Show me your ID.”
  2. Browser checks the chain of trust, domain, dates and revocation.
  3. ID is good, so the server proves it owns the key using a digital signature.
  4. Both sides agree on a fresh secret using ECDHE (this gives PFS).
  5. All data is then encrypted with fast AES.
  6. The 🔒 appears. The password you typed is safe on the way.

PERFECT FORWARD SECRECY (PFS)

Advanced

The scenario

Imagine a spy is recording all your encrypted traffic. He can’t read it today because it’s encrypted. He just saves it and waits.

One year later, he steals the server’s private key.

Question: can he now open all the old recordings?

→ Without PFS: the master key problem

In the old method, the session keys are protected using the server’s one long-term key.

Think of a hotel with one master key:

  • Every room’s lock depends on the master key
  • If someone steals the master key later, they can open every old room
Server's long-term key protects ALL sessions
↓
Spy steals that key a year later
↓
Opens ALL recorded traffic ❌

→ With PFS: a new key every time

With PFS, each conversation uses a fresh, temporary key, made just for that session and thrown away after.

Think of a hotel where every guest gets a new lock that is destroyed after checkout:

  • No master key exists
  • Even if you steal the hotel’s main key today, old rooms are already gone
Session 1 → temporary key A → thrown away
Session 2 → temporary key B → thrown away
Session 3 → temporary key C → thrown away
Spy steals long-term key later → can't recover A, B or C ✅

The long-term key is then used only to prove identity (signing), not to protect the session keys.

Live demo · the spy steals the server's long-term key
🔒Session 1
🔒Session 2
🔒Session 3
Recorded traffic is safe for now. Pick a mode, then steal the key.

How to get PFS

  • ECDHE / DHE are the key exchange methods that make temporary keys. The “E” stands for Ephemeral, which means short-lived.
  • TLS 1.3 has PFS built in, so you can’t turn it off.
  • In TLS 1.2, you must choose cipher suites that start with ECDHE.
🧠 MEMORY TRICK PFS = hotel key cards that self-destruct. The “E” in ECDHE = Ephemeral = Expires quickly. Stolen master key today → yesterday's rooms already gone.
