What is Cloud Security?

Foundation

Cloud security is the set of practices, technologies, and controls designed to protect cloud-based systems, data, and infrastructure from threats. As organizations move workloads from on-premise data centers to the cloud, security responsibilities and threat models fundamentally change.

💡 The Core Shift: Traditional security built walls around a physical perimeter (firewall → everything inside is trusted). Cloud security abandons the perimeter model entirely. In the cloud, identity is the new perimeter — you must assume any user, device, or service could be compromised, and verify everything continuously.
Traditional vs Cloud Security Model

Why Cloud Security is Different

AspectOn-PremiseCloud
PerimeterPhysical firewall, DMZIdentity and IAM policies
Infrastructure controlFull control — you own hardwareShared — CSP manages physical layer
ScalingFixed, slow to changeDynamic — new resources in seconds
Main threatsNetwork intrusion, insiderMisconfigurations, IAM abuse, data exposure
VisibilityLimited — your own logsRich — CloudTrail, Audit Logs, Monitor
Biggest mistakeUnpatched systemsOver-permissive IAM roles & exposed storage
⚠️ The #1 Cloud Security Fact: According to Gartner, 99% of cloud security failures through 2025 are the customer's fault — not the cloud provider. The cloud itself is highly secure. The danger is in how customers configure it.

Cloud Service Models — IaaS, PaaS, SaaS

Core Concept

Cloud services are delivered in three models. Understanding which model you're using is critical because the service model determines who is responsible for what security controls.

Service Model Stack — What You Control vs What CSP Controls
💡 The Security Implication: The more managed the service (SaaS > PaaS > IaaS), the less you control — but the CSP secures more. With IaaS (like EC2), you are responsible for patching the OS, securing the application, and configuring the firewall. With SaaS (like Office 365), you only manage user access and data.

Shared Responsibility Model

Critical Framework

The Shared Responsibility Model defines the security boundary between the Cloud Service Provider (CSP) and the customer. This is the most important concept in cloud security. Every major cloud breach involves a failure to understand this boundary.

🎯 Simple Rule: CSPs are responsible for "Security OF the Cloud" — the hardware, global network, and hypervisor. You are responsible for "Security IN the Cloud" — what you put there, how you configure it, and who can access it.

IAM — Identity & Access Management

Most Critical Skill

IAM is the single most important cloud security topic. Over 80% of cloud breaches involve IAM misconfigurations — either overly permissive roles, exposed access keys, or lack of MFA. Identity is literally the perimeter in cloud security.

💡 Core IAM Concepts:
Principal — Who is making the request (user, role, service account, or application)
Policy — A document that defines what actions are allowed or denied
Least Privilege — Grant only the minimum permissions required to do the job
Role — A set of permissions that can be assumed by users, services, or other AWS accounts

AWS IAM Policy — How It Works

AWS IAM policies are JSON documents. Every API call in AWS is evaluated against these policies. Understanding the structure is essential:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowS3ReadOnly",
      "Effect": "Allow",           // Allow or Deny
      "Action": [
        "s3:GetObject",          // Read objects
        "s3:ListBucket"          // List bucket contents
      ],
      "Resource": [
        "arn:aws:s3:::my-app-bucket",
        "arn:aws:s3:::my-app-bucket/*"
      ],
      "Condition": {
        "StringEquals": {
          "aws:RequestedRegion": "us-east-1"  // Only from this region
        }
      }
    }
  ]
}

// ❌ DANGEROUS — Never do this (grants full admin to everything):
"Action": "*", "Resource": "*"  ←  This is the #1 misconfiguration

IAM Best Practices

1

Never use the Root Account

The root account has unrestricted access to everything. Create an IAM admin user immediately, enable MFA on root, and lock the root credentials away. Never use root for daily tasks — not even for billing.

2

Enable MFA Everywhere

Multi-factor authentication is the single most impactful security control. Require MFA for all IAM users, enforce it via IAM policy conditions, and use hardware keys (YubiKey) for privileged accounts.

3

Use Roles, Not Long-Term Keys

IAM access keys are like passwords that never expire. Instead, use IAM Roles that issue temporary credentials (STS tokens). Applications on EC2 should assume a role — never embed access keys in code or config files.

4

Apply Least Privilege

Start with zero permissions. Grant only what's explicitly needed. Use AWS Access Analyzer to see what permissions an identity actually uses — then remove everything else. Review quarterly.

5

Audit Regularly

Generate IAM credential reports monthly. Delete unused users and rotate old access keys. Use AWS CloudTrail + GuardDuty to alert on unusual IAM activity like role assumption from foreign IPs.

Common IAM Misconfigurations (Attack Vectors)

MisconfigurationRiskFix

Cloud Networking Security — VPC, Firewalls, Segmentation

Core Concept

Cloud networking security involves isolating resources, controlling traffic flow, and preventing unauthorized access between services. Unlike physical networks, cloud networks are software-defined and can be misconfigured with a single click.

VPC — Virtual Private Cloud

A VPC is your own private section of the cloud — an isolated virtual network where you launch resources. Think of it as your own data center inside AWS/Azure/GCP. Everything inside is private by default; you explicitly open what you want exposed.

Key Networking Components (AWS)

ComponentWhat It DoesSecurity Role
Security GroupInstance-level stateful firewallControls what traffic reaches individual EC2 instances
NACL (Network ACL)Subnet-level stateless firewallBroad controls — allow/deny entire CIDRs at subnet boundary
Internet GatewayAllows public internet accessIf attached to subnet → resources can be internet-exposed
NAT GatewayOutbound internet, no inboundPrivate subnets reach internet without being reachable from it
VPC EndpointPrivate connection to AWS servicesAccess S3, DynamoDB without traffic leaving AWS network
VPC Peering / Transit GWConnect multiple VPCsEnable cross-VPC traffic; can create lateral movement paths if misconfigured
Flow LogsLog all network trafficEssential for forensics, anomaly detection, compliance

Critical Networking Misconfigurations

  • 0.0.0.0/0 in Security Group — Allows ANY IP to connect to that port. Never allow SSH (22) or RDP (3389) from 0.0.0.0/0 publicly.
  • Public subnet with no firewall — Resources in public subnets are internet-reachable. Always use Security Groups to restrict ports.
  • Unrestricted egress — Outbound 0.0.0.0/0:all allows any data to leave your environment — potential exfiltration path.
  • Direct database in public subnet — Databases (RDS, MongoDB) should always be in private subnets with no internet gateway route.
# AWS CLI — Audit security groups for dangerous 0.0.0.0/0 rules
aws ec2 describe-security-groups \
  --query 'SecurityGroups[?IpPermissions[?IpRanges[?CidrIp==`0.0.0.0/0`]]].{Name:GroupName,ID:GroupId}' \
  --output table

# Check for publicly accessible RDS instances
aws rds describe-db-instances \
  --query 'DBInstances[?PubliclyAccessible==`true`].DBInstanceIdentifier'

# Enable VPC Flow Logs (should be on in every VPC)
aws ec2 create-flow-logs \
  --resource-type VPC \
  --resource-ids vpc-12345678 \
  --traffic-type ALL \
  --log-destination-type cloud-watch-logs \
  --log-group-name /aws/vpc/flowlogs

Data Security & Encryption in the Cloud

Data Protection

Data is the ultimate target of most cloud attacks. Cloud security requires protecting data at rest (stored), in transit (moving between services), and in use (being processed). Encryption is non-negotiable in regulated industries.

Encryption at Rest

All data stored in cloud services should be encrypted. Most CSPs offer server-side encryption (SSE) managed by the provider — but for sensitive data, you should use customer-managed keys (CMK) so only you control decryption.

ServiceAWSAzureGCP
Object Storage EncryptionS3 SSE-S3, SSE-KMS, SSE-CAzure Storage Service EncryptionCloud Storage + Cloud KMS
Database EncryptionRDS encrypted at rest (AES-256)Azure SQL TDE (Transparent Data Encryption)Cloud SQL + CMEK
Key ManagementAWS KMS (FIPS 140-2)Azure Key VaultCloud KMS + Secret Manager
Disk EncryptionEBS encrypted volumesAzure Disk Encryption (BitLocker/DM-Crypt)Persistent Disk encryption

Encryption in Transit

  • Always enforce TLS 1.2+ — Disable older SSL/TLS versions on load balancers and API gateways
  • Use HTTPS endpoints only — S3 bucket policies can enforce aws:SecureTransport: true to reject HTTP requests
  • Encrypt inter-service communication — Even traffic inside your VPC should use TLS (service mesh or mTLS for microservices)
  • Certificate management — Use AWS Certificate Manager (ACM) or Azure Key Vault for automated TLS certificate rotation

Data Classification

Not all data needs the same protection. Classify your data first, then apply appropriate controls:

ClassificationExamplesRequired Controls
PublicMarketing website, public APIsBasic integrity, availability
InternalInternal docs, employee emailsAccess control, audit logs
ConfidentialSource code, financial dataEncryption, MFA, DLP
Restricted (PII/PHI/PCI)SSNs, health records, card dataEncryption + CMK, strict IAM, compliance audits, DLP
✅ S3 Bucket Security Checklist (the most common misconfiguration target):
  • Block all public access at account level (AWS Block Public Access)
  • Enable server-side encryption (SSE-KMS for sensitive data)
  • Enable versioning + MFA delete for critical buckets
  • Enable access logging and S3 server access logs
  • Use bucket policies to enforce HTTPS (aws:SecureTransport)
  • Enable AWS Macie to automatically detect sensitive data (PII) in S3

☠️ Real Attack Chain: SSRF → Cloud Breach

Case Study

This is the most common and devastating cloud attack path in 2025. It was used in the Capital One breach (2019) — 106 million customer records stolen. Understanding this chain is essential for both attackers and defenders.

⚠️ The Golden Endpoint: Every cloud VM (EC2, Azure VM, GCP Compute) has a special internal IP address 169.254.169.254 — the Instance Metadata Service (IMDS). It provides configuration data including temporary IAM credentials. If an attacker can make your server request this URL (via SSRF), they steal your cloud identity.
Phase 1 — Initial Access
Discover SSRF Vulnerability in Web App
Attacker finds a web application that fetches URLs provided by users — like an image resizer, link previewer, or PDF generator. The server makes HTTP requests on behalf of the user without proper input validation.
GET /fetch?url=http://internal-server/secret-page HTTP/1.1 → Server fetches the URL and returns content (SSRF confirmed)
Phase 2 — Cloud Metadata Theft
Query IMDS to Steal IAM Credentials
The attacker points the SSRF at the IMDS endpoint. The EC2 instance dutifully fetches its own metadata — including the temporary IAM credentials assigned to the instance role.
GET /fetch?url=http://169.254.169.254/latest/meta-data/iam/security-credentials/ → Response: {"AccessKeyId":"ASIA...","SecretAccessKey":"...","Token":"...","Expiration":"..."}
Phase 3 — IAM Enumeration
Use Stolen Credentials to Map the Environment
The attacker uses the stolen temporary credentials from a remote server. They first enumerate what the role can access — listing S3 buckets, EC2 instances, and IAM permissions.
$ export AWS_ACCESS_KEY_ID="ASIA..." $ export AWS_SECRET_ACCESS_KEY="..." $ export AWS_SESSION_TOKEN="..." $ aws sts get-caller-identity → Confirms who we are $ aws s3 ls → Lists ALL accessible buckets $ aws iam list-attached-role-policies --role-name WAF-Role → Check permissions
Phase 4 — Privilege Escalation
Assume Higher-Privilege Role (If Available)
If the compromised role has sts:AssumeRole permission, the attacker can pivot to more powerful roles — potentially reaching admin level. In Capital One's case, the WAF role had read access to 700+ S3 buckets.
$ aws sts assume-role \ --role-arn arn:aws:iam::TARGET:role/AdminRole \ --role-session-name pwned-session → New credentials with elevated permissions returned
Phase 5 — Impact (Capital One Result)
Mass Data Exfiltration + Cover Tracks
The attacker downloads data from all accessible S3 buckets. In Capital One: 30GB of credit application data, 106 million customer records including SSNs and credit scores. Then attempts to disable CloudTrail logging to blind defenders.
$ aws s3 cp --recursive s3://capital-one-sensitive-bucket/ ./exfil/ $ aws cloudtrail stop-logging --name main-trail ← Cover tracks → NOT DETECTED for 4 months until someone found the data on GitHub

How to Defend Against This Attack

Attack StepDefense
SSRF in web appBlock server-side requests to 169.254.0.0/16, validate all URLs, use SSRF-safe HTTP libraries, WAF rules
IMDS credential theftEnforce IMDSv2 — requires token-based auth before serving metadata (blocks simple SSRF)
Over-privileged EC2 roleLeast privilege — WAF role should only access WAF logs, not S3 data buckets
Role chaining/assumptionRemove sts:AssumeRole * — restrict to specific role ARNs
CloudTrail disabledAlert on cloudtrail:StopLogging, enable CloudTrail Log File Validation, send to separate security account
 
# DEFENSE: Enforce IMDSv2 (blocks SSRF credential theft)
aws ec2 modify-instance-metadata-options \
  --instance-id i-1234567890abcdef0 \
  --http-tokens required \          # Require session token (IMDSv2)
  --http-put-response-hop-limit 1   # Block reverse proxies from reaching IMDS

# DETECTION: CloudWatch alert on CloudTrail stop-logging event
# Event pattern to catch attackers trying to go blind:
{
  "source": ["aws.cloudtrail"],
  "detail-type": ["AWS API Call via CloudTrail"],
  "detail": {
    "eventName": ["StopLogging", "DeleteTrail", "UpdateTrail"]
  }
}

Zero Trust Architecture in the Cloud

Modern Security

Zero Trust is a security model based on the principle: "Never trust, always verify." Instead of assuming everything inside your network is safe, Zero Trust requires continuous verification of every user, device, and service — regardless of where they are.

💡 Why Zero Trust for Cloud? The traditional "castle and moat" model doesn't work in the cloud because there IS no castle wall. Employees access cloud resources from anywhere — coffee shops, home offices, airports. Devices may be personal or compromised. The only constant is identity. Zero Trust makes identity the verification checkpoint for every access request.
🔐
Verify Identity
Authenticate every user and service every time. Use MFA, conditional access policies, and identity risk signals to validate every login.
📏
Least Privilege
Grant minimum access needed, just-in-time. Use time-limited roles (PIM/PAM) instead of permanent admin access. Review regularly.
🔬
Assume Breach
Design as if attackers are already inside. Segment networks, encrypt everything, monitor all activity, and minimize blast radius.
🔬
Inspect Traffic
Analyze all traffic — including encrypted east-west (internal) traffic. Use micro-segmentation and service mesh for intra-cluster communication.
📊
Monitor Everything
Collect and analyze all logs. Build behavioral baselines. Use ML-based anomaly detection to spot unusual access patterns in real time.

Zero Trust Implementation in AWS (Example)

# Step 1: Require MFA via IAM condition — no MFA = access denied
{
  "Effect": "Deny",
  "Action": "*",
  "Resource": "*",
  "Condition": {
    "BoolIfExists": {
      "aws:MultiFactorAuthPresent": "false"  // Deny if no MFA
    }
  }
}

# Step 2: Restrict access by IP (corporate VPN only)
"Condition": {
  "NotIpAddress": {
    "aws:SourceIp": ["203.0.113.0/24"]  // Deny if NOT corp IP
  }
}

# Step 3: Enable AWS IAM Identity Center (SSO) with short session tokens
aws sso-admin create-permission-set \
  --session-duration PT1H \   # Sessions expire after 1 hour
  --relay-state https://console.aws.amazon.com/

Detection

In the cloud, you have more logging capability than in traditional environments — every API call, network flow, and configuration change is logged. The challenge is making sense of thousands of events per second and detecting the signal in the noise.

High-Priority CloudTrail Alerts (Must-Monitor Events)

  • cloudtrail:StopLogging — Attacker trying to go dark
  • iam:CreateUser, iam:AttachUserPolicy * — Backdoor account creation
  • sts:AssumeRole from unusual IP/geography
  • s3:GetObject on sensitive buckets by unrecognized principals
  • ec2:AuthorizeSecurityGroupIngress with 0.0.0.0/0
  • guardduty:DeleteDetector — Attacker disabling threat detection
  • kms:DisableKey or kms:ScheduleKeyDeletion — Ransomware preparation
  • Console login from new country or unusual time
📌 SIEM Integration: For enterprise environments, forward cloud logs to Microsoft Sentinel, Splunk, or Elastic SIEM. AWS Security Lake aggregates logs across accounts in OCSF format. Azure Sentinel natively ingests Azure activity logs. With a SIEM, you can write detection rules that correlate across log sources — e.g., "root login + IAM user creation + CloudTrail stopped within 5 minutes = likely compromise."

Container & Kubernetes Security

Cloud Native

Containers (Docker) and Kubernetes (K8s) are now the dominant way to deploy cloud applications. They introduce an entirely new attack surface on top of the existing cloud security concerns.

Docker Container Security Basics

  • Never run containers as root — Use USER in Dockerfile to run as non-root
  • Use minimal base images — Alpine Linux (5MB) vs Ubuntu (70MB). Fewer packages = smaller attack surface
  • Scan images for vulnerabilities — Trivy, Snyk, AWS ECR image scanning, Clair
  • Never expose Docker socket — Mounting /var/run/docker.sock inside a container gives container escape capability
  • Read-only filesystem — Mount container filesystem as read-only where possible
  • Drop Linux capabilities — Remove capabilities like NET_ADMIN, SYS_ADMIN not needed by the app

Kubernetes Security — The 4Cs Model

C1

Cloud

Secure the underlying cloud infrastructure. IAM for EKS/AKS/GKE cluster access, node group security groups, private API endpoints.

C2

Cluster

Kubernetes RBAC (Role-Based Access Control), NetworkPolicies to restrict pod-to-pod traffic, admission controllers (OPA Gatekeeper, Kyverno) to enforce security policies.

C3

Container

Secure container images — no root, minimal base, vulnerability-free. Pod Security Standards (PSS) enforce security contexts across namespaces.

C4

Code

Secure the application code itself — SAST, DAST, dependency scanning, secrets detection in CI/CD pipeline before deployment to K8s.

# Kubernetes NetworkPolicy — Deny all inter-pod traffic by default (Zero Trust)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: production
spec:
  podSelector: {}         # Applies to ALL pods in namespace
  policyTypes:
  - Ingress
  - Egress              # Block both directions by default

# Then explicitly allow only what's needed:
# Allow frontend → backend on port 8080 only
---
kind: NetworkPolicy
spec:
  podSelector:
    matchLabels:
      app: backend
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend
    ports:
    - port: 8080

Serverless Security — Lambda, Functions & APIs

Cloud Native

Serverless (AWS Lambda, Azure Functions, GCP Cloud Functions) eliminates the need to manage servers. The CSP handles OS patching and runtime. But serverless introduces unique security challenges around IAM, secrets management, and cold start attacks.

Serverless Attack Surface

Attack VectorHow It HappensDefense
Overpermissive Lambda RoleLambda function's IAM role has *:* — compromise of function = full cloud accessLeast privilege per-function role. Never share roles between functions.
Secrets in Environment VariablesDeveloper puts DB password in Lambda env var — visible in AWS console, logsUse AWS Secrets Manager or SSM Parameter Store (encrypted)
SSRF via LambdaLambda fetches user-controlled URLs — can reach IMDS at 169.254.169.254IMDSv2 enforcement, input validation, block IMDS URL patterns in WAF
Event InjectionMalicious data in SQS/SNS/S3 event payload that Lambda processes — leads to injection attacksValidate and sanitize all event data before processing
Dependency Vulnerabilitiesnpm/Python packages bundled with Lambda have known CVEsScan dependencies in CI/CD (Snyk, OWASP Dependency-Check)
✅ Serverless Security Quick Wins:
Use one IAM role per Lambda function (not a shared role)
Store secrets in AWS Secrets Manager, not environment variables
Enable AWS Lambda function URL auth or API Gateway auth — never expose functions unauthenticated
Enable AWS X-Ray for distributed tracing and anomaly detection
Set memory and timeout limits — excessive execution time is a DoS indicator

Incident Response in Cloud Environments

IR

Cloud IR is faster and has more tooling than traditional IR — but also has unique challenges like ephemeral resources (containers disappear), shared infrastructure, and cross-account activity. The PICERL framework applies, but cloud-specific steps are critical.

Cloud IR Playbook — Compromised IAM Credentials

1

Contain Immediately — Revoke the Key

Do NOT wait to investigate first. Immediately: aws iam delete-access-key --access-key-id AKIA... or attach a Deny-All policy to the compromised user. Contain first, investigate second.

2

Determine Blast Radius

Query CloudTrail for all actions taken with the compromised key in the last 24-48 hours: aws cloudtrail lookup-events --lookup-attributes AttributeKey=AccessKeyId,AttributeValue=AKIA...

3

Identify Created Resources

Check for new IAM users, EC2 instances, S3 buckets, or Lambda functions created during the compromise window. Attackers often create persistence mechanisms — backdoor IAM users, scheduled tasks.

4

Preserve Evidence

Export CloudTrail logs, VPC Flow Logs, and EBS snapshots before terminating compromised resources. Cloud forensics requires logs — without them you lose the investigation trail forever.

5

Eradicate & Recover

Delete attacker-created resources, rotate all credentials (not just the compromised one), apply SCPs to prevent recurrence, and restore from clean snapshots/backups.

6

Post-Incident Improvements

Enable GuardDuty if not running, implement credential scanning in CI/CD (prevent key commits), set up AWS Config rules for continuous compliance, and conduct security training.

# Cloud IR — Complete compromised key investigation script

# 1. Immediately attach Deny-All to compromised user
aws iam put-user-policy --user-name compromised-user \
  --policy-name EMERGENCY-DENY-ALL \
  --policy-document '{"Version":"2012-10-17","Statement":[{"Effect":"Deny","Action":"*","Resource":"*"}]}'

# 2. Find all API calls made with compromised key (last 90 days)
aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=AccessKeyId,AttributeValue=AKIAIOSFODNN7EXAMPLE \
  --start-time 2025-05-01 \
  --query 'Events[].{Time:EventTime,Name:EventName,Source:SourceIPAddress}'

# 3. List all active IAM sessions (find stolen session tokens)
aws iam list-access-keys --user-name compromised-user

# 4. Check for new IAM users/roles created by attacker
aws iam list-users --query 'Users[?CreateDate>="2025-05-18"].UserName'

Cloud Penetration Testing Techniques

Offensive

Cloud pentesting (offensive security in cloud environments) follows the same methodology as traditional pentesting but with cloud-specific tools and techniques. Always obtain written authorization and check CSP pentesting policies before testing.

⚠️ Legal Requirement: AWS, Azure, and GCP all have penetration testing policies. AWS allows most testing without prior authorization, but prohibits DNS zone walking, DoS testing, and port flooding. Always check the current policy and ensure you have a signed Statement of Work. Unauthorized cloud testing is a criminal offense.
